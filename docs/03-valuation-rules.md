# 估值规则

本文定义估值口径。机读版本在 `backend/app/data/seed/0002_rule_config.sql`，
页面提供查看 / 修改 / 恢复默认入口，每次变更写入 `rule_config_version` 并记入
`run_manifest`，保证「同一输入可复现同一结果」。

> 口径由会计/金融方向同学拍板并对本文负责。改动口径请改 `rule_config` 的**数据**，
> 不要改代码。

---

## 一、为什么周期股需要特殊处理

能源钢铁属强周期行业。**在周期高点上，FCFF 会因为产品价格暴涨而虚高**，直接拿去做
永续增长等于把周期顶部当成常态，估值结果会离谱地乐观；周期底部则反之。

这是钢铁煤炭估值最经典、也最容易被金融方向评委当场抓到的错误。

解决办法是用**穿越一个完整周期的中枢盈利能力**替代单年数据，作为 DCF 预测的起点。
这个动作叫**正常化（normalization）**。

---

## 二、周期正常化口径

### 窗口

| 项 | 取值 | 说明 |
|---|---|---|
| 主窗口 | **8 个完整财务年度** | 锚定最新完整年度滚动 |
| 主窗口最少可比年度 | **7 个** | 不足则自动扩展 |
| 回退窗口 | **10 个完整财务年度** | 主窗口不达标时启用 |
| 回退窗口最少可比年度 | **8 个** | 仍不足则拒绝出分 |

**窗口锚定最新完整年度滚动，不人为挑选区间。** 以 2024 年报为最新完整年度时：
主窗口 `2017—2024`，回退窗口 `2015—2024`。

加入 2025 年报后自动滚动为 `2018—2025` / `2016—2025`。

> 不采用「2016—2023」这类不含最新年度的窗口——它容易被质疑为挑了对自己有利的区间。

### 核心指标

**收入加权的周期中位 EBIT margin。**

```
中枢 = 收入加权分位数(各年 EBIT margin, q = 0.5)
```

**为什么不用简单算术平均**：周期里小年度的利润率会被异常放大（分母小），算术平均会
让这些年份获得与其经济权重不相称的影响。若某年收入占窗口九成，它的利润率就应当主导
中枢。

**四分位（p25 / p75）用同一种加权方式**。若中枢收入加权而 p25/p75 未加权，情景映射
（`mapping.medium.delta` 取 `historical_p25`）拿到的区间与中枢就来自两套口径，两者之差
不再有经济含义。

### 高低盈利阶段覆盖校验

窗口必须**同时包含显著高于与显著低于自身中枢的年份**，否则判为 `incomplete_cycle`，
拒绝正常化。

判定用**相对中枢的绝对落差**（默认 2 个百分点），不是分位数：

```
高盈利年 = { y : margin_y ≥ 中枢 + 2% }
低盈利年 = { y : margin_y ≤ 中枢 − 2% }
```

> ⚠ **为什么不能用分位数判定**：对任何给定的窗口，分位数总能找到「最高的那个」和
> 「最低的那个」，校验会恒为真，拦不住任何东西。用绝对落差才能拦住「全是平淡年份」
> 的窗口——所有年份都挤在中枢附近时，两个条件同时不成立。

### 不可比年度：三步流程，不自动删除

1. 先标记为 `non_comparable` 并写明原因
2. 由会计同学判断是否存在重大重组、资产注入、合并范围变化、前期重述或会计政策变更
3. 确认后从**主中枢**计算中排除，但**在敏感性分析中保留**

`方案选择.docx` 明确了这一点：这比简单剔除 2023—2024 年的大额减值更容易被金融评委接受。

### 失败时拒绝出分

```
8 年窗口可比年度 < 7  →  扩展至 10 年
10 年窗口可比年度 < 8 →  返回 NORMALIZATION_INSUFFICIENT_DATA
```

**失败时不得输出任何中枢值**，连一个「带警告的数字」都不给。这条由数据库 `CHECK`
约束强制：

```sql
CHECK (status NOT IN ('NORMALIZATION_INSUFFICIENT_DATA','incomplete_cycle')
       OR (ebit_margin_mid IS NULL AND ebit_margin_p25 IS NULL AND ebit_margin_p75 IS NULL))
```

> 如果失败也返回数字，哪怕附警告，界面一定会把它渲染成一个大号分数，人工复核入口
> 就形同虚设。下游 DCF 拿不到值就只能拒绝计算——这是刻意的设计。

## 三、EBIT 口径

三套算法并存，**禁止只保留一个**。

### Reported EBIT（主 DCF 默认）

```
Reported EBIT = 利润总额 + 利息费用 − 利息收入
```

历史轻解析阶段唯一能算出来的口径，也是**会计同学批准调整之前 DCF 唯一允许使用的口径**。

### Cross-check EBIT（仅核对）

```
Cross-check EBIT = 营业利润 + 财务费用
```

仅在年报数据齐备时可用。它包含投资收益等非经营项，与 Reported EBIT 天然存在口径差，
因此只用于**交叉核对**：两法差异超过 **5%** 时进入 `needs_review`。

### Adjusted EBIT（需逐笔批准）

```
Adjusted EBIT = Reported EBIT − 非核心收益 + 非核心损失
                + 经批准加回的一次性费用 − 经批准剔除的一次性收益
```

**每一笔调整都必须留下**：原始项目名称、调整金额、调整方向、调整理由、来源页码、
复核状态。未获会计逐笔批准前，DCF 一律使用 Reported EBIT，调整结果只进敏感性分析。

### 非经常性损益的处理原则

| 项目 | 默认处理 |
|---|---|
| 政府补助 | 一次性补助剔除；持续性经营补贴可保留 |
| 资产处置收益/损失 | 非日常处置剔除 |
| 投资收益 | 非主营投资收益剔除；与主营高度相关且持续发生的联营/合营收益可保留，但需单独标记 |
| 公允价值变动 | 非主营金融资产收益通常剔除 |
| 套期保值 | 为原材料或产品风险管理且持续发生的保留；投机性或一次性交易剔除 |
| **资产减值** | **不机械剔除，逐年判断** |
| 重组费用 | 一次性且不反映持续经营能力的可加回 |
| 关联交易影响 | 若存在非市场化定价，进入人工复核 |

### 资产减值为什么不机械剔除

如果减值反映的是产能过剩、资产竞争力下降或长期盈利恶化，**不加回**——那正是周期底部
的真实经营状况，加回等于粉饰。

只有有充分证据证明减值是一次性、非重复且不代表持续经营能力下降时，才可以加回。

主模型同时保存**报告 EBIT、调整后 EBIT、调整理由和来源**三项。

## 四、交叉验证（一律不影响 DCF）

以下四项**仅作参考**，用于回答「EBIT margin 中枢这个结论稳不稳」。核心中枢只能来自
`normalization_run.ebit_margin_mid`，这一点由 `NormalizationCrosscheck` 的
`affects_dcf` 字段强制为 `False`。

### 吨钢毛利

**优先采用公司年报直接披露的吨钢毛利或吨钢 EBITDA。** 自行计算时：

```
吨钢毛利 = (钢材销售收入 − 钢材销售成本) / 钢材销售量
```

销售成本须包含公司披露口径下的**材料、人工、制造费用和折旧**，不能只减原材料成本。

> ⚠ 若只能得到「钢材售价 − 原材料成本」，**必须命名为「吨钢原料差价」，不得称为
> 吨钢毛利**——两者相差了人工、制造费用与折旧，量级可能差一倍。

**分母用销售量。**

### 产能利用率

采用公司披露的**有效产能利用率**，不以设计产能作为默认口径。

- 一体化钢企：`粗钢产量 / 有效粗钢产能`
- 轧钢企业：`钢材产量 / 有效钢材产能`
- **不能混用粗钢产能和钢材产量**

对应的字段键（签字文档 A-5）：`crude_steel_output` / `crude_steel_effective_capacity`、
`steel_output` / `steel_effective_capacity`。字典里刻意把它们做成**四个独立字段**
而不是一个 `effective_capacity` 加一句说明：混用粗钢与钢材分母不会报错，
只会得到一个大于 100% 或明显偏低的利用率，**必须靠字段本身挡住**。
`crude_steel_capacity`（粗钢产能，属设计/公告口径）是补充字段，**不进分母**。

不同公司口径不同，必须原样保存并标注。**分母用产量**（与吨钢毛利相反）。

**产能利用率只用于判断周期阶段和经营状态，不直接进入 DCF 公式。**

### EBITDA margin

作为 EBIT margin 的合理性交叉检验。两者应同向变动；若严重背离，说明折旧摊销政策
或资本开支结构有异常，需人工复核。

### ROIC

```
ROIC = NOPAT / 平均投入资本
NOPAT = 调整后 EBIT × (1 − 正常化税率)
投入资本 = 股东权益 + 有息负债 + 租赁负债 − 超额现金 − 非经营性金融投资
```

- **取期初期末平均值**，不用单一时点值
- **主口径保留商誉**，因为商誉是企业实际投入资本的一部分
- 同时提供**扣除商誉 ROIC** 作为敏感性分析
- **两种口径不得混用**

交叉验证指标推算的中枢与核心 EBIT margin 中枢相差超过 20% 时，标记为需要人工复核。

## 五、DCF 规则

- **主模型为 FCFF**，明确 EBIT、税率、折旧摊销、资本开支、营运资本变化、WACC 与终值增长率
- **企业价值到股权价值**：扣除有息负债、租赁负债等约定净债务项目，加回非经营性现金和
  投资，除以**稀释后股本**
- **终值默认用永续增长法**，并**必须并列展示退出倍数校验**——周期股的 EV/EBITDA 本身
  也随周期波动，两法对不齐时必须说明原因
- **终值增长率默认不超过长期通胀**（上限 2%）。周期行业不给高永续增速
- **周期位置必须显式标注**（高点 / 中枢上方 / 中枢 / 中枢下方 / 低点 / 未知），
  并作为情景权重的输入之一。让评委看到系统知道自己在周期的哪里，而不是假装周期不存在
- 吨钢毛利、产能利用率、钢材价格等行业变量，全部标记为 `model_assumption` 或
  `user_input`，**不得由模型凭记忆填入**

### 参数来源必须标记

每个参数标记为以下四类之一，禁止无来源：

| 来源类型 | 含义 |
|---|---|
| `historical_fact` | 历史事实，必须指向具体的 `fact_id` |
| `user_input` | 用户输入，必须记录 `user:<uid>` |
| `comparable_stat` | 可比公司统计，必须指向 `comparable_id` |
| `model_assumption` | 模型假设，必须记录假设键 |

## 六、相对估值规则

- 支持 PE、EV/EBITDA 或 PB
- **可比公司必须记录**：行业、细分行业、业务相似性、规模、成长性、盈利状态、数据日期、
  **选择理由**
- **亏损公司不得机械使用 PE**——`PE` 函数的签名里就有 `profitable: bool` 参数，
  亏损时直接返回 `refused`
- 输出中位数、区间和异常值说明（异常值剔除需留痕）
- **同一细分行业方可互为可比**。煤价是钢企的成本项，两者周期驱动因素相反，把煤企当作
  钢企的估值可比公司会让中位数失去意义
- 产业链上游公司只能以 `chain_reference` 身份作为产业链分析参考，
  **不得进入估值可比集**

---

## 七、敏感性分析

至少展示两组：

1. **WACC × 永续增长率**
2. **收入增速 × 利润率**

另需提供**诊断指数传导前后对照**，展示哪些参数因哪条证据发生了变化。

**估值输出永远是区间，不是单一目标价。**

---

## 八、诊断指数向估值的透明传导

诊断指数**不得黑箱式修改目标价**，只能通过预先公开的映射规则影响情景参数。

| 触发条件 | 基准/乐观/压力权重 | 参数调整 | 用户可见提示 |
|---|---|---|---|
| 一致性较高（≥70）且财务质量稳定 | 0.60 / 0.25 / 0.15 | 增长取历史中位数，WACC 不变 | 「一致性较高，保持基准」 |
| 部分冲突（45–69） | 0.50 / 0.20 / 0.30 | 收入增速取历史下四分位，WACC +0.5pct | 「证据部分冲突，压低增长假设」 |
| 一致性低（<45）或存在方向相反观测 | 0.35 / 0.15 / 0.50 | 增速取下四分位×0.9，WACC +1.0pct，终值增长率 −0.5pct | 「扩大估值区间」 |
| 证据不足或不可比占多数 | **不变** | **不自动改参数** | 「未传导至估值，仅提示人工复核」 |

每次参数变化均显示「**原参数 — 新参数 — 触发证据 — 适用边界**」，用户可以恢复默认值。

**指数永不单独生成买卖指令。**

## 九、复算要求

估值结果必须可被 Excel 手工复算：

- 预测期逐年现金流的明细全部落库（`valuation_output`），含 EBIT / NOPAT / D&A /
  Capex / ΔNWC / FCFF / 折现因子 / 现值，每行带公式与输入
- 所有计算走纯函数（无 `now()`、无全局状态），同输入必同输出
- `run_manifest` 记录代码版本、依赖锁哈希、输入文件 sha256、模型名与版本、
  prompt 注册表哈希、规则版本、随机种子
- `scripts/replay_task.py --task-id <id>` 一条命令重建并比对 `output_hash`
